## 1. سبب التحديث وما أدخلته نتائج البحث الموضوعي على المشروع

جاء هذا التحديث نتيجة مراجعة البحث الموضوعي المتعلق بالتخطيط للانتقال، وبخاصة العلاقة بين التقييم الانتقالي، ملف المتعلم، الأولويات الفردية، الخطة التربوية/الانتقالية، المنهج الوظيفي، التنفيذ، الأدلة الوظيفية، والمراجعة وإعادة التخطيط.

أظهرت القراءة البحثية أن المشروع لا ينبغي أن يُبنى على نموذج خطي واحد من نوع "تقييم → هدف → نشاط"، ولا على افتراض أن أداة تقييم واحدة أو الخطة نفسها تمثل الحقيقة الكاملة عن المتعلم. لذلك تم إدخال التحولات المعمارية الآتية:

1. اعتماد **ملف المتعلم** كسجل طولي مستمر للحقائق والأدلة والتاريخ المقبول، وليس كسجل تابع للخطة أو لمحرك المراجعة.
2. الفصل بين:
   - **Transition Concepts / Domains** بوصفها طبقة تنظيم وتغطية؛
   - **Competencies** بوصفها قدرات وظيفية متكاملة؛
   - **Enabling Skills** بوصفها مكونات أصغر قابلة للتعليم والتدخل؛
   - **Performance/Access Dimensions** بوصفها أبعاد أداء عابرة مثل التعميم والاستبقاء واستخدام الدعم والسلامة السياقية.
3. اعتبار **المنهج الوظيفي** طبقة تطبيق ودمج وأداء في سيناريوهات حياتية ذات معنى، وليس قائمة أنشطة تابعة للأهداف الفردية.
4. اعتماد دورة تعلم طولية:
   **ملف المتعلم → التخطيط → الخطة → التنفيذ/الأدلة → المراجعة → تعلم مقبول بشريًا → الدورة التالية**.
5. عدم السماح للمراجعة أو المنهج أو الذكاء الاصطناعي بإنشاء حقيقة جديدة عن المتعلم بصورة تلقائية.
6. إدخال بنية versioned تسمح بإضافة تصنيفات لاحقة بعد CVI دون إعادة كتابة التاريخ السابق.
7. التعامل مع نتائج البحث الحالية باعتبارها أساسًا معماريًا وتصميميًا، مع فصل واضح بين:
   - دليل خارجي راسخ؛
   - سوابق نماذج تطبيقية؛
   - تركيب معقول؛
   - فرضية تصميم للمشروع؛
   - محتوى يحتاج تحققًا تجريبيًا أو تحكيمًا خارجيًا.

وبذلك لم يغيّر البحث واجهة المشروع أو الرحلة الإنتاجية الحالية مباشرة؛ بل أدخل **طبقة معمارية وحوكمية مضافة** تحمي الرحلة الحالية وتجهزها للانتقال المنضبط بعد التحقق العلمي.

## 3. حالة المحتوى البحثي وشرط رفع وسم pre_cvi

### 3.1 الحالة الحالية

جميع العناصر الآتية تحمل حالة **`pre_cvi`**:

- Gate A.
- الكفاءات المرشحة الـ22.
- أبعاد الأداء/الوصول:
  - PD01 — Generalization.
  - PD02 — Maintenance.
  - PD03 — Effective Support Use.
  - PD04 — Contextual Functional Safety.
- العلاقات الدلالية الحالية بين المفاهيم والكفاءات المرشحة.
- أي استنتاجات merge/gap/retain المرتبطة بها بوصفها قرارات محتوى نهائية.

وجود هذه العناصر في الكود لا يعني أنها أصبحت taxonomy معتمدة أو صالحة للاستخدام الإنتاجي.

### 3.2 شرط رفع الوسم

لا يجوز رفع أي عنصر من `pre_cvi` إلى `validated` لمجرد:

- نجاح build أو tests؛
- اكتمال البرمجة؛
- desk review؛
- توافقه مع البحث النظري؛
- توافقه مع المصفوفة الحالية؛
- أو نجاح نموذج اصطناعي.

شرط الرفع هو **اكتمال تحكيم CVI الخارجي المخصص لذلك العنصر، واستلام نتائج قابلة للمراجعة، وتحليلها واتخاذ قرار موثق بشأن الإبقاء أو التعديل أو الدمج أو الحذف أو إعادة التصنيف**.

### 3.3 صاحب قرار رفع الوسم

قرار رفع الوسم لا يملكه:

- الكود؛
- محرك الذكاء الاصطناعي؛
- محرك مراجعة الخطط؛
- نتيجة اختبار تقني؛
- أو crosswalk آلي.

القرار يملكه **صاحب السلطة العلمية/الحوكمية المفوضة للمشروع وفق MASTER-GOVERNING-PLAN**، بعد مراجعة نتائج CVI واعتمادها بشريًا بصورة صريحة وموثقة. ويمكن للخبراء أو لجنة CVI تقديم الحكم العلمي، لكن الانتقال في سجل المشروع من `pre_cvi` إلى `validated` يحتاج قرار الحوكمة المعتمد، ولا يحدث تلقائيًا.

## 4. نطاق الربط مع smart-iep-engine

### 4.1 الفرضيات الست للربط

تم اعتماد ست فرضيات وظيفية مستقلة ومتكاملة، وليس علاقة واحدة بين النظامين:

1. **Plan Quality Gate**  
   تمر مسودة الخطة على محرك المراجعة قبل الاعتماد، وتعود ملاحظات الجودة إلى الخطة.

2. **Profile ↔ Plan Consistency Review**  
   يستطيع المحرك — عند تفعيل الربط لاحقًا — قراءة Snapshot محدود من ملف المتعلم ومقارنة الخطة بالأدلة والتاريخ والأولويات المقبولة.

3. **Plan-only Correction**  
   الملاحظات التي تخص صياغة الخطة أو القياس أو baseline أو التكرار أو الاتساق تبقى ملاحظات على الخطة ولا تدخل ملف المتعلم.

4. **Longitudinal Review Learning**  
   بعض نتائج المراجعة يمكن أن تتحول إلى Learning Candidates تتعلق بالتاريخ التخطيطي أو علاقات الأهداف أو الحاجة لجمع دليل إضافي، لكنها لا تصبح حقيقة إلا بعد اعتماد بشري.

5. **Inline Quality Support**  
   يمكن مستقبلًا استخدام بعض قدرات المراجعة أثناء بناء الخطة نفسها لتقديم تنبيه جودة، دون منح المحرك سلطة إنشاء أو اعتماد هدف.

6. **Shared Knowledge Alignment**  
   يتشارك النظامان لغة مرجعية versioned للمفاهيم والكفاءات والمهارات الممكنة وأبعاد الأداء والأدلة، دون دمج قواعد البيانات أو جعل أحد النظامين مالكًا لبيانات الآخر.

### 4.2 ما تم تنفيذه حتى هذا القرار

تم تنفيذ البنية التحضيرية للفرضيات التالية:

- **Plan Quality Gate:** العقد قادر على فصل Plan Findings وإبقائها في مسار الخطة.
- **Profile ↔ Plan Consistency:** تم تعريف Profile Snapshot وعناصر المقارنة، لكن الوصول الحقيقي غير مفعّل.
- **Plan-only Correction:** تم تثبيت الوجهة `PLAN_ONLY` لملاحظات الخطة.
- **Longitudinal Review Learning:** تم تعريف Learning Candidates وقرار القبول/الرفض/التعديل وAccepted Review Learning.
- **Shared Knowledge Alignment:** تم تضمين مراجع versioned للكيانات الانتقالية دون ربطها تلقائيًا بمحتوى Gate A.
- **Inline Quality Support:** ما زال فرضية مستقبلية ولم يُربط بواجهة بناء الخطة أو رحلة المستخدم الحالية.

في `smart-iep-engine` تم إعداد الجانب المقابل للعقد والمحول والاختبارات على فرع التكامل، لكن لا يوجد اتصال إنتاجي أو endpoint مشترك مفعل في هذه المرحلة.

### 4.3 القيود الثابتة

حتى صدور قرار حوكمة جديد، تظل القيود التالية إلزامية:

- ملف المتعلم هو مصدر الحقيقة المقبولة عن المتعلم.
- وصول محرك المراجعة إلى Profile Snapshot — عند تفعيله — يكون **للقراءة فقط**.
- طبقة النقل الحالية **للبيانات الاصطناعية فقط**.
- `realDataAllowed = false`.
- لا كتابة مباشرة من محرك المراجعة إلى ملف المتعلم.
- لا إنشاء هدف تلقائيًا من Review Finding أو Learning Candidate.
- لا تغيير مستوى كفاءة أو أداء تلقائيًا.
- لا نقل تشخيص أو اعتباره مدخلًا حاكمًا للملف.
- لا استخدام اسم المتعلم كمفتاح ربط بين النظامين؛ الربط يحتاج معرفًا صريحًا ومقصودًا.
- Plan Findings لا تحدث ملف المتعلم.
- Profile Comparison Findings تحتاج مراجعة بشرية.
- Learning Candidates تحتاج قرارًا بشريًا صريحًا.
- فقط Accepted Review Learning يمكن أن يصبح مدخلًا في التاريخ التخطيطي، وبحسب نوعه ووجهته المعتمدة.
- لا direct shared storage ولا دمج قواعد بيانات بين المشروعين.
- لا endpoint binding حقيقي قبل المرحلة التالية المصرح بها.
- لا يُسمح للمراجعة القديمة/stale review أن تحكم دورة تخطيط جديدة دون مراجعة صلاحيتها.

## 6. ما ينتظر قبل أي خطوة تالية

لا يبدأ أي توسع جديد في الربط قبل تنفيذ التسلسل التالي:

### المرحلة 1 — توحيد العقد المشترك

الهدف هو منع drift بين النسختين الموجودتين من بروتوكول `himam-review-integration-v1`.

يجب قبل أي اتصال HTTP:

- مقارنة تعريفات العقد في المستودعين.
- توحيد الأسماء والحقول والحالات والنسخة.
- تحديد مصدر واحد أو آلية versioning مشتركة للعقد.
- تثبيت compatibility rules بين الإصدارات.
- الحفاظ على استقلال المستودعين وعدم فرض shared database.

هذه هي **الخطوة التالية المباشرة** بعد هذا القرار.

### المرحلة 2 — اختبار HTTP تجريبي

بعد توحيد العقد فقط:

- إنشاء endpoint تجريبي محدود.
- feature flag مغلق افتراضيًا.
- بيانات اصطناعية فقط.
- Profile Snapshot باتجاه المحرك للقراءة فقط.
- Review Package في الاتجاه العكسي.
- لا persistence على ملف متعلم حقيقي.
- لا automatic push/write-back.
- التحقق من المصادقة، الإصدار، rejection paths، traceability، ومنع أي payload غير synthetic.

نجاح هذا الاختبار لا يرفع أي محتوى من `pre_cvi`.

### المرحلة 3 — ما بعد CVI

لا يبدأ الانتقال إلى المحتوى الحاكم أو التفعيل التدريجي إلا بعد:

1. اكتمال نتائج CVI.
2. قرار حوكمة موثق بشأن كل عنصر متأثر.
3. تسجيل scheme/version جديد بدل إعادة كتابة التاريخ.
4. مراجعة crosswalk النهائي.
5. اختبارات synthetic/deidentified.
6. اعتماد بشري للانتقال.
7. اتباع خطة `post-cvi-migration-plan.ts` بما فيها dual-read/legacy-write والrollback.
8. عدم تفعيل Model C إلا بعد استيفاء بواباته المستقلة.

## 7. القرار الحاكم في هذه النقطة

يُعتمد الوضع الحالي بوصفه **Architecture & Integration Foundation — Pre-CVI / Non-Production**.

المسموح حاليًا:

- الحفاظ على الطبقة المعمارية المضافة.
- توثيقها واختبارها.
- توحيد العقد المشترك بين المستودعين.
- إجراء اختبارات اصطناعية لا تؤثر على البيانات الحقيقية.

غير المسموح دون قرار لاحق:

- دمج هذا الفرع إلى `main`.
- تفعيل API على بيانات حقيقية.
- رفع Gate A أو الكفاءات الـ22 أو PD01–PD04 إلى `validated`.
- استخدام Gate A لإعادة تصنيف بيانات قديمة.
- إنشاء أهداف أو تعديل ملف المتعلم تلقائيًا من نتائج المراجعة.
- تشغيل عقود post-CVI كمنطق إنتاجي.
- فتح Model C.

**الخطوة المصرح بها التالية فقط:** توحيد العقد المشترك، ثم — بعد تحقق منفصل — إعداد اختبار HTTP اصطناعي.
