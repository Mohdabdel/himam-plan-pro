## 0. طريقة استخدام هذه الوثيقة

هذه الوثيقة لا تستخدم منفردة كأمر تنفيذ برمجي. نطاق الـMVP هنا مشروط بما يلي:

- لا تستخدم أي مسودة خارجية من GitHub أو Lovable أو محادثة سابقة قبل تسجيلها في Evidence Inventory.
- لا تتحول قراءة الملف إلى دليل أو قرار دون مسودة استخراج ومراجعة مختص.
- لا تضيف الواجهة حالة اعتماد دون GoalApprovalRecord أو PlanApprovalRecord.
- لا يضاف AI أو وسائط أو صلاحيات قبل المرور عبر سياسة الحوكمة والجاهزية.

## 1. المستخدم

المستخدم الأساسي في النسخة الأولى هو المختص المسؤول عن بناء خطة انتقال أو خطة تربوية فردية مدعومة بالأدلة لشاب أو متعلم من ذوي الإعاقة داخل مركز أو مؤسسة.

احتياجاته الأساسية:

- إدخال متعلم جديد بسرعة وبنية واضحة.
- جمع مصادر معلومات متعددة دون تحويلها مباشرة إلى أحكام نهائية.
- رفع ملفات نتائج التقييم أو النماذج المطبقة وقراءتها قراءة منظمة قابلة للمراجعة.
- رؤية كفاية المعلومات والفجوات قبل بناء الأهداف.
- مراجعة دعم معرفي أثناء إعداد الخطة دون تحويل هذا الدعم إلى قرار آلي.
- توليد مسودة هدف قابلة للقياس من فرصة أو دليل أو مؤشر.
- اعتماد الهدف كوحدة قابلة للإدراج في الخطة، مع بقاء اعتماد الخطة الكاملة لصاحب صلاحية أعلى.

المستخدمون الثانويون في النسخة الأولى:

- الأسرة، كمصدر رؤية وأولوية وسياق.
- المتعلم، كمصدر تفضيلات واهتمامات ورؤية.
- المختص الأعلى أو المراجع المعتمد، كصاحب صلاحية مراجعة الأهداف كوحدات ومراجعة الخطة العامة كوحدة متكاملة.

## 2. المشكلة

المشكلة التي يعالجها المنتج هي أن بناء خطط الانتقال والأهداف التربوية غالباً يحدث عبر نصوص حرة أو انطباعات غير كافية التتبع، مما يؤدي إلى:

- أهداف لا ترتبط بمستوى الأداء الحالي.
- خلط بين الدليل الأدائي والمعلومة الداعمة.
- استخدام صوت الأسرة أو المتعلم كحكم أداء مباشر بدلاً من كونه سياقاً وأولوية.
- الاكتفاء باسم الملف المرفوع دون قراءة محتواه أو استخراج مؤشرات قابلة للمراجعة.
- ضعف معرفة المختص بما إذا كانت المعلومات كافية لبناء خطة.
- صعوبة تتبع التقرير أو الهدف إلى مصدره الأصلي.
- صعوبة الحكم على جودة الخطة العامة إذا تم التعامل مع كل هدف بمعزل عن اتساق الخطة الكاملة.

منصة همم تعالج ذلك عبر مسار منظم:

```text
مصادر معلومات
→ تصنيف ومعالجة
→ مؤشرات وفجوات وفرص
→ أهداف قابلة للقياس
→ مراجعة بشرية
→ تنفيذ وشواهد
→ تقرير قابل للتتبع
```

## 3. الرحلة الأساسية

رحلة MVP المقبولة:

```text
إنشاء متعلم
→ إدخال البيانات الأساسية
→ اختيار أداة تقييم رسمية ورفع أو إدخال نتائجها
→ قراءة ملف التقييم المرفوع واستخراج مسودة منظمة قابلة لمراجعة المختص
→ إدخال أو رفع صوت المتعلم وقراءة النموذج المرفوع إن وجد
→ إدخال أو رفع صوت الأسرة وقراءة النموذج المرفوع إن وجد
→ إضافة مصدر معلومات إضافي اختيارياً وقراءة ملفه إن وجد
→ فتح كفاية المعلومات
→ رؤية مؤشرات ودلائل وفجوات وفرص
→ فتح إعداد الخطة
→ فتح شاشة دعم المعرفة أثناء إعداد الخطة
→ إعداد هدف واحد من فرصة أو مصدر
→ مراجعة جودة الهدف واعتماده للإدراج في الخطة
→ تكرار إعداد الأهداف حسب الحاجة
→ مراجعة الخطة العامة كوحدة متكاملة
→ إرسال الخطة لاعتماد المختص الأعلى
```

قواعد الرحلة:

- لا اعتماد آلي للخطة.
- لا اعتماد آلي للهدف.
- اعتماد المختص للهدف يعني صلاحيته للإدراج في الخطة، لا اعتماد الخطة النهائية.
- اعتماد الخطة النهائية يتم على مستوى أعلى يراجع الأهداف كوحدات ويراجع اتساق الخطة ككل.
- لا مستوى أداء نهائي دون مراجعة بشرية.
- لا تقرير بلا تتبع للمصادر.
- لا استخدام لمصدر داعم كدليل أداء مباشر.
- لا تستخدم قراءة الملف المرفوع كمصدر حاكم وحدها؛ يجب أن تنتج مسودة استخراج قابلة للمراجعة والتصحيح.

## 4. الشاشات

شاشات النسخة الأولى:

1. لوحة المختص
   - عرض المتعلمين قيد العمل.
   - إنشاء متعلم جديد.
   - استكمال بروفايل موجود.

2. إدخال البيانات الأساسية
   - اسم المتعلم.
   - العمر أو تاريخ الميلاد.
   - التشخيص كسياق فقط.
   - المركز أو المؤسسة.
   - المختص المسؤول.

3. فهرس مصادر جمع المعلومات
   - أداة التقييم الرسمية.
   - صوت المتعلم.
   - صوت الأسرة.
   - مصادر إضافية.
   - مراجعة كفاية المعلومات.

4. صفحة أداة التقييم الرسمية
   - تسجيل الأداة.
   - رفع نتائج التقييم أو التقرير.
   - قراءة الملف المرفوع واستخراج نتائج أو مؤشرات منظمة حسب نوع الملف وحدود الترخيص.
   - عرض مسودة القراءة للمختص للمراجعة والتعديل والتأكيد.
   - إدخال نتائج منظمة عند تعذر القراءة أو لاختيار المؤسسة الإدخال اليدوي.
   - حفظ StructuredResponse.
   - تحويل ما يصلح فقط إلى EvidenceRecord.

5. صفحة صوت المتعلم
   - الاهتمامات.
   - التفضيلات.
   - نقاط القوة.
   - رؤية مستقبلية أو بدائل تواصل.
   - رفع نموذج أو أداة مطبقة إن وجد.
   - قراءة الملف المرفوع واستخراج مسودة معلومات داعمة قابلة للمراجعة.
   - تحفظ كمعلومة داعمة لا كدليل أداء مباشر.

6. صفحة صوت الأسرة
   - الأولويات.
   - المخاوف.
   - المدعمات المنزلية.
   - الرؤية المستقبلية.
   - رفع نموذج أو أداة مطبقة إن وجد.
   - قراءة الملف المرفوع واستخراج مسودة معلومات داعمة قابلة للمراجعة.
   - تحفظ كمعلومة داعمة لا كدليل أداء مباشر.

7. صفحة كفاية المعلومات
   - حالة الحد الأدنى.
   - المصادر المكتملة.
   - InformationInsight.
   - GoalOpportunity.
   - SupportOpportunity.
   - InformationGap.

8. فهرس إعداد الخطة
   - مستوى الأداء الحالي.
   - رؤية الخطة.
   - دعم المعرفة.
   - توليد الأهداف.

9. شاشة دعم المعرفة
   - تعرض Specialist Knowledge Support بشكل مقروء أثناء إعداد الخطة.
   - تفصل بين EvidenceRecord وKnowledgeSupportItem وInferenceSuggestion وCompletionGap وOpenConflict.
   - تسمح بتثبيت بطاقة معرفة كسياق أو مرجع للهدف حسب نوعها وحدود أثرها.
   - تعرض Provenance لكل بطاقة معرفة.
   - لا تكتب هدفاً ولا تعتمد قراراً بنفسها.

10. شاشة إعداد الأهداف هدفاً بهدف
   - اختيار المجال.
   - اختيار فرصة أو مصدر.
   - أسئلة توجيهية قصيرة.
   - توليد مسودة هدف بستة عناصر.
   - فحص جودة أولي.
   - ربط الهدف بمصدر أو دليل قابل للتتبع.
   - اعتماد المختص للهدف كوحدة قابلة للإدراج في الخطة.

11. شاشة مراجعة الخطة العامة
   - تعرض جميع الأهداف المعتمدة للإدراج.
   - تعرض اتساق الأهداف مع مستوى الأداء الحالي، الأولويات، الفجوات، والخدمات.
   - تعرض مؤشرات اكتمال الخطة العامة.
   - تسمح بإرسال الخطة للمختص الأعلى أو الجهة الأعلى صلاحية للاعتماد.

12. شاشة اعتماد المختص الأعلى
   - مراجعة كل هدف كوحدة مستقلة.
   - مراجعة الخطة كوحدة متكاملة.
   - قبول الخطة، إعادتها للتعديل، أو طلب استكمال مصادر/أهداف.

13. شاشة تنفيذ الهدف
    - تسجيل جلسات التنفيذ.
    - شواهد التدريب.
    - مستوى الاستقلالية أو التكرار أو المدة.

14. شاشة التقرير
    - تقرير مبني على المصادر، الأهداف، التنفيذ، الشواهد، ومؤشرات التقدم.
    - كل Claim يجب أن يرتبط بمصدر.

## 5. البيانات

كيانات البيانات الأساسية في MVP:

- LearnerProfile
- InformationSource
- UploadedSourceFile
- ExtractedSourceDraft
- SourceExtractionReview
- ToolAdministration
- StructuredResponse
- EvidenceRecord
- KnowledgeSupportItem
- InferenceSuggestion
- InformationInsight
- GoalOpportunity
- SupportOpportunity
- InformationGap
- KnowledgeCard
- GoalKnowledgePin
- GoalBuildHandoff
- GoalDraft
- GoalQualityCheck
- GoalApprovalRecord
- PlanDraft
- PlanQualityReview
- PlanApprovalRecord
- ExecutionWitness
- ReportClaim

قواعد البيانات الحاكمة:

- EvidenceRecord فقط يمكن أن يدخل في حساب مستوى أداء.
- KnowledgeSupportItem يدعم السياق والرؤية ولا يرفع المستوى وحده.
- InferenceSuggestion يبقى مقترحاً حتى يراجعه المختص.
- الملف المرفوع يحفظ كمصدر خام، وما يقرأ منه يحفظ كمسودة استخراج لا كسجل أداء نهائي.
- لا يتحول ExtractedSourceDraft إلى EvidenceRecord أو KnowledgeSupportItem إلا بعد مراجعة المختص وحفظ StructuredResponse.
- نتائج التقييم الرسمية المرفوعة قد تنتج EvidenceRecord فقط عند وجود نتيجة منظمة وسياق وأداة واضحة وقابلية تتبع.
- كل سجل مهم يحتاج SourceRef قابل للتتبع.
- لا يوجد مفهوم خارج سجل مفاهيم همم المعتمد.
- GoalApprovalRecord يثبت صلاحية هدف للإدراج في الخطة، لكنه لا يساوي PlanApprovalRecord.
- PlanApprovalRecord يصدر من المختص الأعلى أو الجهة الأعلى صلاحية بعد مراجعة الخطة كاملة.

## 6. مميزات النسخة الأولى

النسخة الأولى يجب أن تتضمن:

- إنشاء متعلم جديد.
- إدخال البيانات الأساسية.
- تسجيل أداة تقييم رسمية.
- رفع نتائج أداة التقييم الرسمية.
- قراءة ملفات التقييم المرفوعة واستخراج مسودة منظمة قابلة للمراجعة.
- إدخال نتائج منظمة من أداة التقييم عند الحاجة.
- إدخال صوت المتعلم.
- رفع وقراءة نموذج صوت المتعلم إن وجد.
- إدخال صوت الأسرة.
- رفع وقراءة نموذج صوت الأسرة إن وجد.
- إضافة مصدر معلومات إضافي اختياري.
- رفع وقراءة نموذج أو أداة مصدر معلومات إضافي تم تطبيقه.
- تصنيف المصادر إلى EvidenceRecord أو KnowledgeSupportItem أو InferenceSuggestion أو PendingReview.
- صفحة كفاية معلومات تنتج insights وgaps وopportunities.
- شاشة دعم معرفة أثناء إعداد الخطة.
- إعداد الأهداف هدفاً بهدف من فرصة أو مصدر.
- فحص جودة الهدف وفق عناصر قابلة للقياس.
- اعتماد المختص للهدف كوحدة قابلة للإدراج في الخطة.
- مراجعة الخطة العامة كوحدة متكاملة.
- إرسال الخطة لاعتماد مختص أعلى أو جهة أعلى صلاحية.
- تتبع الهدف والمخرجات إلى مصادرها.
- تحقق تقني من build وtypecheck وdata integrity وuser journey وtraceability.

## 7. المميزات خارج نطاق الإصدار الأول

ما يؤجل بعد MVP:

- قراءة متقدمة لجميع صيغ التقييمات دون قوالب أو مراجعة بشرية.
- استخراج آلي كامل للجداول المحمية أو معادلات التصحيح المقيدة ترخيصياً.
- تطبيق أدوات تقييم كاملة داخل المنصة.
- محرك معايرة مستوى متقدم أو نهائي.
- الربط المؤسسي الحقيقي.
- نظام صلاحيات مؤسسي متقدم متعدد الأدوار خارج مسار المختص والمختص الأعلى الأساسي.
- حساب مستقل للأسرة.
- محفظة تعلم كاملة.
- تقارير PDF نهائية احترافية.
- تصدير للأنظمة الخارجية.
- ذكاء اصطناعي توليدي كامل مرتبط بمصادر متعددة.
- نظام تتبع دوري كامل بعد التنفيذ.
- نشر إنتاجي نهائي.

## 8. مؤشر النجاح المخطط

يعد MVP ناجحاً عندما ينجز المختص الرحلة الأساسية كاملة دون كسر قواعد الدليل والتتبع.

مؤشرات النجاح العملية:

- يستطيع المختص إنشاء متعلم جديد وإكمال البيانات الأساسية.
- يستطيع تسجيل مصدر تقييم رسمي واحد على الأقل.
- يستطيع رفع ملف تقييم رسمي وقراءة محتواه كمسودة استخراج قابلة للمراجعة.
- يستطيع رفع نموذج أو أداة مصدر معلومات وقراءة محتواه كمسودة استخراج قابلة للمراجعة.
- يستطيع إدخال صوت الأسرة وصوت المتعلم كمعلومات داعمة.
- تعرض صفحة كفاية المعلومات فجوات وفرصاً قابلة للاستخدام.
- يستطيع المختص فتح شاشة دعم المعرفة وربط بطاقة معرفة مناسبة بهدف دون كسر حدود الأثر.
- يستطيع المختص توليد هدف واحد على الأقل من GoalOpportunity.
- يمر الهدف على فحص جودة أولي.
- يعتمد المختص الهدف كوحدة قابلة للإدراج في الخطة.
- يستطيع المختص تجميع أكثر من هدف داخل خطة عامة.
- يستطيع المختص الأعلى مراجعة الخطة كوحدة متكاملة وقبولها أو إعادتها للتعديل.
- كل هدف أو تقرير أو claim قابل للتتبع إلى مصدر.
- تنجح فحوص التحقق الخمسة:
  - build
  - typecheck
  - dataIntegrity
  - userJourney
  - traceability

## 9. خطة الاستكمال

العمل الحالي لا يحتاج اختراع PRD من الصفر، بل يحتاج تثبيت هذه المسودة كمرجع حاكم وربطها بالتنفيذ.

الخطوات التالية:

1. مراجعة PRD واعتماد أو تعديل نطاق MVP.
2. بناء Gap Analysis محدث للنقاط الثلاث: قراءة الملفات، دعم المعرفة، واعتماد الخطة.
3. تحويل UploadedSourceFile وExtractedSourceDraft وSourceExtractionReview إلى contracts واضحة.
4. تحويل شاشة دعم المعرفة إلى route أو drawer متزامن مع شاشة إعداد الأهداف.
5. فصل GoalApprovalRecord عن PlanApprovalRecord في البيانات والواجهة.
6. تحويل كل شاشة في PRD إلى قائمة مكونات وroutes.
7. تنفيذ Stage 4 أو ترحيل واجهات Stage 2 وStage 3 حسب قرار الأولوية.
8. إضافة اختبار رحلة متصفح كامل من رفع ملف مصدر إلى اعتماد خطة من المختص الأعلى.
9. تحديث وثيقة VerificationRun بعد كل مرحلة.
