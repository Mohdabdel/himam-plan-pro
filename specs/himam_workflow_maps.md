# Himam Workflow Maps

تاريخ الإصدار: 2026-08-23  
آخر تحديث: 2026-08-24  
الحالة: خرائط سير عمل فعلية قابلة للاختبار قبل التصميم والبرمجة

## 1. قاعدة الخرائط

كل مسار عمل في HIMAM يجب أن يصف رحلة مستخدم فعلية لا مجرد انتقال تقني. أي route أو workflow جديد يجب أن يطابق أحد هذه المسارات أو يضيف مساراً حاكماً جديداً قبل البرمجة.

كل مسار يحتوي: نقطة البداية الحقيقية، المستخدم والدور والصلاحية، المعلومات المتاحة عند البداية، قرار المستخدم، ما يضيفه، ما يقترحه النظام، ما يتطلب اعتماداً، الناتج، التدقيق، حالات النقص/الخطأ/التعارض، التوقف في منتصف المهمة، ما يظهر لمستخدم آخر، ما لا يجوز أن يظهر له، زمن الاستخدام المتوقع، وكيف نثبت أن المسار أخف من البديل الحالي.

## 2. مسار الحالة

```text
لوحة المختص
→ إنشاء/فتح حالة متعلم
→ إدخال بيانات أساسية
→ حالة LearnerProfile قابلة للاستكمال
```

| البند | المواصفة |
|---|---|
| نقطة البداية الحقيقية | مختص يفتح لوحة العمل ويريد بدء حالة أو استكمال حالة ناقصة |
| المستخدم والدور والصلاحية | مختص مخول داخل مؤسسة وله علاقة بالحالة أو حق إنشاء حالة |
| المعلومات المتاحة عند البداية | قائمة المتعلمين، حالة الرحلة، بيانات تعريفية متاحة، مركز/مؤسسة، موافقة أولية إن وجدت |
| ما الذي يقرره؟ | إنشاء حالة جديدة، فتح حالة موجودة، أو ترك الحالة حتى تتوفر موافقة/بيانات أساسية |
| ما الذي يضيفه؟ | الاسم/المعرف، العمر أو تاريخ الميلاد، المؤسسة، المختص المسؤول، سياق أولي |
| ما الذي يقترحه النظام؟ | AgeStage advisory، نقص الحد الأدنى، آخر مرحلة مفتوحة |
| ما الذي يتطلب اعتماداً؟ | لا اعتماد مهني في هذه الخطوة؛ الاعتماد يظهر لاحقاً في الهدف/الخطة/التقرير |
| ما الذي ينتج عنه؟ | LearnerProfile draft أو active مع حالة رحلة واضحة |
| ما الذي يسجل في التدقيق؟ | createdBy, createdAt, assignedSpecialist, changedFields, consentState |
| النقص/الخطأ/التعارض | نقص عمر، غياب مؤسسة، موافقة غير معروفة، تكرار حالة محتملة |
| عند التوقف في المنتصف | تحفظ كمسودة غير مكتملة مع حقول ناقصة ولا تظهر كجاهزة للتخطيط |
| ما يظهر لمستخدم آخر؟ | المراجع يرى اسم الحالة وحالة الاكتمال إذا له علاقة/غرض |
| ما لا يجوز أن يظهر له؟ | بيانات حساسة أو مصادر أو تقارير لمن لا علاقة له بالحالة |
| زمن الاستخدام المتوقع | 2-5 دقائق للحالة الأساسية |
| إثبات أنه أخف من البديل | قياس عدد الحقول الإلزامية أقل من نموذج ورقي كامل، وعدم إعادة إدخال الهوية لاحقاً |

## 3. مسار الأدلة والملف الحالي

```text
إضافة مصدر
→ رفع ملف أو إدخال نموذج
→ قراءة الملف
→ ExtractedSourceDraft
→ مراجعة المختص
→ StructuredResponse
→ EvidenceRecord / KnowledgeSupportItem / InferenceSuggestion / PendingReview
→ كفاية معلومات
```

| البند | المواصفة |
|---|---|
| نقطة البداية الحقيقية | المختص لديه تقرير/أداة/نموذج أو يريد تسجيل مصدر معلومات |
| المستخدم والدور والصلاحية | مختص له علاقة بالحالة وغرض جمع معلومات؛ AI مقيد إن وجد |
| المعلومات المتاحة عند البداية | LearnerProfile، قائمة المصادر، metadata سابقة، حالة الموافقة، أدوات مسجلة |
| ما الذي يقرره؟ | رفع ملف، إدخال نتائج يدوياً، مراجعة مسودة استخراج، أو تسجيل فشل قراءة |
| ما الذي يضيفه؟ | نوع المصدر، اسم الأداة/النموذج، تاريخ، ملف/نتائج، سياق، ملاحظات مراجعة |
| ما الذي يقترحه النظام؟ | استخراج، تصنيف أولي، فشل قراءة، نقص metadata، تعارض محتمل، فجوة كفاية |
| ما الذي يتطلب اعتماداً؟ | تحويل مسودة extraction إلى StructuredResponse أو EvidenceRecord يتطلب مراجعة مختص |
| ما الذي ينتج عنه؟ | UploadedSourceFile, ExtractedSourceDraft, SourceExtractionReview, StructuredResponse, Evidence/KSI/Inference |
| ما الذي يسجل في التدقيق؟ | uploader, file metadata, extraction status, reviewer, decision, failure reason, sourceRef |
| النقص/الخطأ/التعارض | ملف غير قابل للقراءة، ملف محمي، نقص metadata، مصدر مسحوب الموافقة، تعارض مصدرين |
| عند التوقف في المنتصف | يبقى UploadedSourceFile وExtraction status = needs_review أو failed ولا يتحول إلى دليل |
| ما يظهر لمستخدم آخر؟ | المراجع يرى حالة المصدر، قرار المراجعة، والفجوات إذا له صلاحية |
| ما لا يجوز أن يظهر له؟ | محتوى ملف حساس أو وسائط أو raw extraction لمن لا يملك purpose/relationship |
| زمن الاستخدام المتوقع | 3-8 دقائق للمصدر البسيط؛ 10-20 دقيقة لمراجعة ملف طويل |
| إثبات أنه أخف من البديل | مقارنة عدد مرات نسخ النتائج يدوياً؛ قياس نسبة reuse من StructuredResponse في الهدف والتقرير |

## 4. مسار كفاية المعلومات

```text
مصادر مصنفة
→ فحص تغطية وثقة وتعارض
→ InformationInsight / InformationGap
→ GoalOpportunity / SupportOpportunity
```

| البند | المواصفة |
|---|---|
| نقطة البداية الحقيقية | المختص يريد معرفة هل تكفي المعلومات لبدء هدف أو يحتاج استكمال مصدر |
| المستخدم والدور والصلاحية | مختص الحالة أو مراجع مخول |
| المعلومات المتاحة عند البداية | مصادر مراجعة، EvidenceRecords، KSI، تعارضات، حالة الموافقة، مفاهيم مغطاة |
| ما الذي يقرره؟ | الاستكمال، المتابعة بهدف محدد، أو تسجيل سبب التقدم رغم نقص محدود |
| ما الذي يضيفه؟ | مبرر التقدم أو طلب استكمال أو تعليق تعارض |
| ما الذي يقترحه النظام؟ | فجوات، فرص هدف، فرص دعم، تعارضات مفتوحة، مستوى ثقة |
| ما الذي يتطلب اعتماداً؟ | تجاوز نقص جوهري يحتاج مبرر مسجل؛ لا يعد اعتماد خطة |
| ما الذي ينتج عنه؟ | InformationInsight, InformationGap, GoalOpportunity, SupportOpportunity |
| ما الذي يسجل في التدقيق؟ | sufficiencyCheckId, checkedBy, gaps, conflicts, proceedReason |
| النقص/الخطأ/التعارض | مصدر واحد فقط، سياق ناقص، أدلة متعارضة، موافقة مسحوبة |
| عند التوقف في المنتصف | تبقى الفجوات مفتوحة ولا تعرض الفرصة كجاهزة |
| ما يظهر لمستخدم آخر؟ | حالة كفاية مختصرة والفجوات المهنية لا raw data غير مصرح |
| ما لا يجوز أن يظهر له؟ | تفاصيل حساسة للمصدر إذا كان يرى فقط summary أو review status |
| زمن الاستخدام المتوقع | 2-6 دقائق إذا المصادر منظمة؛ أكثر عند التعارض |
| إثبات أنه أخف من البديل | قياس عدد الفجوات المكتشفة قبل كتابة الهدف وتقليل إعادة فتح الأهداف الناقصة |

## 5. مسار الهدف والخطة

```text
حاجة/فرصة
→ دعم معرفة
→ هدف مرشح
→ مسودة هدف
→ فحص جودة
→ اعتماد هدف للإدراج
→ خطة عامة
→ مراجعة خطة
→ اعتماد أعلى
```

| البند | المواصفة |
|---|---|
| نقطة البداية الحقيقية | توجد حاجة/أولوية أو GoalOpportunity ويريد المختص صياغة هدف قابل للقياس |
| المستخدم والدور والصلاحية | المختص يعد الهدف؛ المختص الأعلى أو جهة أعلى تعتمد الخطة |
| المعلومات المتاحة عند البداية | أداء حالي، أدلة، KSI، بطاقات معرفة، فجوات، تعارضات، أهداف سابقة |
| ما الذي يقرره؟ | اختيار فرصة/مصدر، قبول مسودة هدف، تعديلها، اعتمادها للإدراج، أو إعادتها للنقص |
| ما الذي يضيفه؟ | السلوك، الشرط، المعيار، طريقة القياس، السياق، مبرر الاعتماد |
| ما الذي يقترحه النظام؟ | صياغة مسودة، فحص جودة، مصادر مرتبطة، تنبيه KSI، اتساق الخطة |
| ما الذي يتطلب اعتماداً؟ | GoalApprovalRecord للهدف، PlanApprovalRecord للخطة من دور مخول |
| ما الذي ينتج عنه؟ | GoalDraft, GoalQualityCheck, GoalApprovalRecord, PlanDraft, PlanQualityReview, PlanApprovalRecord |
| ما الذي يسجل في التدقيق؟ | goal draft create/update, quality check, approval decision, plan review, actor role, rationale |
| النقص/الخطأ/التعارض | هدف بلا baseline، KSI كcriterion، خطة بلا أهداف معتمدة، تعارض غير مفسر |
| عند التوقف في المنتصف | الهدف يبقى draft ولا يدخل الخطة؛ الخطة تبقى draft ولا تصبح نهائية |
| ما يظهر لمستخدم آخر؟ | المختص الأعلى يرى الهدف، مصادره، جودة الهدف، والخطة كوحدة |
| ما لا يجوز أن يظهر له؟ | زر اعتماد خطة لمختص غير مخول أو اعتماد بلا مبرر/تدقيق |
| زمن الاستخدام المتوقع | 5-12 دقيقة للهدف الواحد؛ 10-20 دقيقة لمراجعة خطة قصيرة |
| إثبات أنه أخف من البديل | قياس نسبة إعادة استخدام PLAAFP والمصادر، وعدد الأهداف المرفوضة بسبب نقص العناصر |

## 6. مسار الجلسة والممارسة

```text
هدف معتمد
→ جلسة/ممارسة
→ ملاحظة أو قياس
→ ExecutionWitness
→ Progress signal
```

| البند | المواصفة |
|---|---|
| نقطة البداية الحقيقية | منفذ أو مختص يسجل أداءً بعد تنفيذ هدف معتمد |
| المستخدم والدور والصلاحية | مختص أو مساعد مخول بعلاقة حالة وغرض تنفيذ |
| المعلومات المتاحة عند البداية | الهدف، السياق، الدعم، معيار القياس، آخر قياس، خطة التنفيذ |
| ما الذي يقرره؟ | تسجيل جلسة، إضافة شاهد، أو ترك الجلسة ناقصة |
| ما الذي يضيفه؟ | تاريخ، سياق، قيمة/ملاحظة أداء، مستوى دعم، شاهد إن وجد |
| ما الذي يقترحه النظام؟ | نقص حقول، قابلية المقارنة، تنبيه تعميم، اتجاه تقدم أولي |
| ما الذي يتطلب اعتماداً؟ | لا اعتماد خطة؛ اعتماد احتساب تقدم رسمي قد يتطلب مراجعة مختص |
| ما الذي ينتج عنه؟ | ExecutionWitness, ProgressMeasurement, follow-up note |
| ما الذي يسجل في التدقيق؟ | recordedBy, timestamp, goalId, changedFields, evidence attachment, context |
| النقص/الخطأ/التعارض | جلسة ناقصة، قياس لا يطابق criterion، اتصال منقطع، شاهد بلا موافقة |
| عند التوقف في المنتصف | تسجل كمسودة جلسة أو لا تحتسب كتقدم رسمي حتى اكتمال الحد الأدنى |
| ما يظهر لمستخدم آخر؟ | المراجع يرى اتجاه التقدم وسجل القياس إذا له صلاحية |
| ما لا يجوز أن يظهر له؟ | وسائط حساسة أو raw notes لمن لا يملك غرض viewing |
| زمن الاستخدام المتوقع | 1-4 دقائق للجلسة البسيطة |
| إثبات أنه أخف من البديل | قياس سرعة تسجيل جلسة مقارنة بنموذج ورقي، وعدم إعادة كتابة الهدف أو المعيار |

## 7. مسار التقرير والتتبع

```text
ReportClaim
→ EndToEndTrace
→ owning entity
→ SourceRef
→ Source/Tool/File
```

| البند | المواصفة |
|---|---|
| نقطة البداية الحقيقية | المختص أو المراجع يريد تقريراً قابلاً للتتبع من خطة وبيانات مراجعة |
| المستخدم والدور والصلاحية | مختص أو مراجع مخول؛ مشاركة التقرير تحتاج purpose وrecipient |
| المعلومات المتاحة عند البداية | LearnerProfile، مصادر، أهداف، خطة، قرارات، تنفيذ، فجوات، تعارضات |
| ما الذي يقرره؟ | معاينة، طلب استكمال، إصدار رسمي، أو تصدير/مشاركة |
| ما الذي يضيفه؟ | نطاق التقرير، مبرر الإصدار أو المشاركة، مستلم، مدة صلاحية عند المشاركة |
| ما الذي يقترحه النظام؟ | Claims مع مصادرها، missing evidence warnings، conflicts, report sections |
| ما الذي يتطلب اعتماداً؟ | إصدار التقرير الرسمي ومشاركته خارج السياق الداخلي |
| ما الذي ينتج عنه؟ | ReportDraft, ReportClaim, IssuedReport, Export/Share event |
| ما الذي يسجل في التدقيق؟ | generatedBy, issuedBy, sourceRefs, claims, recipient, export fields, timestamp |
| النقص/الخطأ/التعارض | Claim بلا مصدر، تضارب مفتوح، مصدر مسحوب الموافقة، صلاحية مشاركة ناقصة |
| عند التوقف في المنتصف | يبقى ReportDraft ولا يصدر؛ تظهر أسباب المنع عند العودة |
| ما يظهر لمستخدم آخر؟ | المراجع يرى تقريراً مع trace وmissing evidence إذا له صلاحية |
| ما لا يجوز أن يظهر له؟ | روابط وسائط مفتوحة، raw files، أو claims بلا مصدر كأنها حقيقة |
| زمن الاستخدام المتوقع | 3-8 دقائق لمعاينة تقرير جاهز؛ أطول عند الفجوات |
| إثبات أنه أخف من البديل | قياس عدد claims التي تولدت من sourceRefs تلقائياً، وتقليل تجميع التقرير اليدوي |
