# Himam Build Cycle 05 Execution Plan

تاريخ الإصدار: 2026-08-30  
الحالة: بوابة ما قبل البرمجة لمحرك جودة الهدف والخطة  
النطاق: تحويل مراجع جودة الهدف والخطة ومعالجة البروفايل إلى Rubric تشغيلية مهنية لا تصدر قراراً ولا تعتمد هدفاً أو خطة.

## 1. قرار منتج مرجعي

بعد مراجعة دستور ما قبل البرمجة، لا تبدأ دورة جودة الهدف والخطة من تحسين واجهة أو من SMART وحدها. تبدأ من قرار منتج حاكم:

- الهدف وحدة قابلة للمراجعة قبل إدراجها في الخطة.
- الخطة وحدة متكاملة تحتاج مراجعة أعلى من مجرد جمع أهداف جيدة منفردة.
- حفظ الهدف كمسودة لا يساوي إقرار المختص للهدف ولا يرفعه لمسار الخطة أو اعتماد المشرف.
- جودة الهدف تعتمد على مصدر، خط أساس، حاجة، أولوية، صياغة قابلة للقياس، طريقة قياس، وسياق تنفيذ.
- في شاشة الهدف يفصل مصدر الهدف إلى `باعث الهدف` و`مرتكز الأداء / الخط القاعدي`؛ الأول يفسر لماذا نختار الهدف، والثاني يثبت الأداء الحالي الذي لا يعتمد الهدف بدونه.
- جودة الخطة تعتمد على اتساق الأهداف مع مستوى الأداء الحالي، مصادر المعلومات، الفجوات، الخدمات، والتخطيط الانتقالي عند عمر 14 فأعلى.
- صوت الأسرة والمتعلم يحسن الأولوية والمعنى والتخصيص، لكنه لا يصبح baseline أو criterion دون دليل أداء مراجع.

## 2. سيناريو مستخدم محدد

كمختص، بعد أن يختار مجالاً أو فرصة هدف، يرى فحص جودة لا يكتفي بسؤال "هل الهدف SMART؟"، بل يوضح:

- هل توجد مصادر وأدلة أو بروفايل مراجع يدعم الهدف؟
- هل باعث الهدف منفصل عن مرتكز الأداء؟
- هل خط الأساس واضح وقابل للتتبع؟
- هل الحاجة والأولوية مثبتتان أو مفسرتان؟
- هل المعيار وطريقة القياس مناسبان؟
- هل استخدمت معلومات الأسرة والمتعلم في التخصيص دون تحويلها إلى دليل أداء؟
- هل توجد فجوة تمنع اعتماد الهدف أم تنبيه يحسن جودة الصياغة؟

كمختص أعلى، عند مراجعة الخطة، يرى:

- جودة كل هدف كوحدة.
- اتساق الخطة كوحدة متكاملة.
- تغطية المجالات والمكونات الأساسية للبروفايل.
- فجوات الانتقال لعمر 14 فأعلى.
- ما يمنع الاعتماد وما يسمح بالتقدم مع مبرر.

## 3. متطلبات مجال وصلاحيات

طبقات المجال التي تمسها الدورة:

- `Evidence`: لا يعتمد الهدف بلا مصدر أو دليل مناسب عندما يكون المعيار أو baseline أدائياً.
- `KSI`: يستخدم للتخصيص والأولوية، ولا يستخدم كمستوى أداء أو criterion.
- `Inference`: كل توصية جودة تبقى اقتراح مراجعة لا قراراً.
- `Decision`: لا ينتج المحرك `GoalApprovalRecord` أو `PlanApprovalRecord`.
- `Audit`: أي اعتماد لاحق يجب أن يبقى عبر مسارات الاعتماد الحالية.

الصلاحيات:

- المختص يرى Rubric الهدف ويعدل الهدف أو يسجل مبرر التقدم.
- المختص الأعلى يرى Rubric الخطة العامة عند المراجعة.
- لا تضيف هذه الدورة صلاحية اعتماد جديدة.
- لا تضيف AI إنتاجي أو قراءة ملفات جديدة.

## 4. تصميم بيانات مع migration قابلة للمراجعة

لا توجد migration في هذه الدورة. التصميم المطلوب طبقة مشتقة داخل الذاكرة من البيانات القائمة:

```text
LearnerProfileProcessingModel.componentMatrix
GoalDraft / goal form fields
GoalQualityInput
PLAN_QUALITY_CRITERIA
TRANSITION_ASSESSMENT_PRINCIPLES
→ GoalPlanQualityRubricResult
```

العقود المقترحة لاحقاً في الكود:

- `QualityFindingSeverity = "blocking" | "warning" | "advisory"`
- `QualityFindingScope = "goal" | "plan" | "transition"`
- `QualityFindingSource = "evidence" | "profile_component" | "goal_text" | "measurement" | "plan_coherence" | "transition_reference"`
- `GoalPlanQualityRubricResult`

أي تخزين دائم لهذه النتائج يحتاج قراراً لاحقاً. في هذه الدورة تكون النتائج مشتقة وقابلة لإعادة الحساب.

## 5. API أو service contract

العقد البرمجي المطلوب قبل ربط الواجهة:

```text
evaluateGoalPlanQuality(input) → GoalPlanQualityRubricResult
```

المدخلات:

- بيانات الهدف أو الخطة.
- باعث الهدف.
- مرتكز الأداء / الخط القاعدي.
- نموذج معالجة البروفايل.
- عناصر مصفوفة المكونات ذات الصلة.
- مراجع جودة الخطة.
- مبادئ تقييم الانتقال.
- عمر المتعلم أو مرحلة العمر إذا كانت متاحة.

المخرجات:

- `blockingFindings`: تمنع اعتماد الهدف أو الخطة.
- `warnings`: تنبه لجودة أو اتساق ناقص.
- `advisories`: تحسينات مهنية غير مانعة.
- `sourceReferences`: المعايير أو المراجع الداخلية التي استند إليها الفحص.
- `reviewSummaryAr`: صياغة عربية مهنية للمختص.

حدود العقد:

- لا ينتج قرار اعتماد.
- لا يمنع حفظ المسودة داخل مساحة العمل، لكنه يمنع رفع الهدف لمسار الخطة عند وجود ملاحظات مانعة.
- لا يستخدم نسب أو أوزان غير معتمدة.
- لا يحسب scoring سيكومتري.
- لا يخمن نقص baseline أو criterion.

## 6. تصميم واجهة

تظهر نتائج Rubric في:

- شاشة إعداد الأهداف هدفاً بهدف.
- شاشة Goal Studio وفق التصور 1 المعتمد مع تحسينات الفصل بين باعث الهدف ومرتكز الأداء.
- لوحة دعم معرفي تعمل في الخلفية وتستدعى عند الطلب، أو تظهر موازية فقط في مسار الكتابة المستقلة دون الأسئلة الموجهة.
- شاشة مراجعة الخطة العامة.
- شاشة اعتماد المختص الأعلى عند عرض الخطة كوحدة.

أول 30 ثانية:

- يرى المستخدم ملخصاً واضحاً: مانع اعتماد، تنبيه جودة، أو توصية تحسين.
- يرى سبب كل بند ومصدره.
- يرى ما يجب استكماله دون إعادة إدخال معلومات موجودة.
- يستطيع حفظ الهدف كمسودة متضمنة الملاحظات المانعة دون إنشاء `GoalApprovalRecord`.
- توسم المسودة بوضوح: `قابلة للاستكمال` أو `غير قابلة للتقدم قبل استيفاء موانع التقدم`.
- تفاصيل الموانع لا تعرض افتراضياً؛ تظهر عند طلب المختص فقط حتى لا تتحول الشاشة إلى ازدحام معلومات.
- لا يظهر خيار إقرار الأهداف ورفعها لمسار الخطة إلا بعد استيفاء الملاحظات المانعة.
- إذا اختار مسار الأسئلة الموجهة، لا تزاحمه لوحة الدعم المعرفي المفتوحة افتراضياً.
- إذا اختار الكتابة المستقلة، يستطيع فتح الدعم المعرفي كلوحة موازية منظمة.

رسالة غياب الدليل:

```text
لا يمكن اعتبار هذا الهدف جاهزاً للاعتماد لأن خط الأساس أو المصدر الأدائي غير كاف. يمكن تعديل الهدف أو استكمال مصدر أو تسجيل سبب تقدم محدود وفق الصلاحية.
```

ما لا يجوز للنظام تخمينه:

- baseline.
- باعث الهدف.
- criterion.
- أولوية الأسرة.
- رغبة المتعلم.
- مناسبة الهدف للانتقال إذا لم يوجد عمر أو سياق كاف.

## 7. اختبارات حسب المخاطر

التحقق المطلوب لدورة 05:

- `npm run verify:build-cycle-05`
- `npm run verify:plan-quality`
- `npm run verify:transition-assessment`
- `npm run verify:build-cycle-04`
- `npm run verify:governing-files`
- `npm run typecheck`
- `npm run lint`
- `npm run build`

الاختبارات السلبية المطلوبة عند التنفيذ:

- هدف بصياغة جيدة لكنه بلا baseline ينتج blocking.
- هدف يستخدم KSI كcriterion ينتج blocking.
- هدف عليه `blockingFindings` يحفظ كمسودة فقط ولا ينشئ `GoalApprovalRecord`.
- هدف لعمر 14 فأعلى بلا ربط انتقالي ينتج warning أو advisory حسب السياق، لا اعتماد آلي.
- خطة بأهداف منفردة جيدة لكن بلا اتساق عام تنتج plan warning.
- Rubric لا ينشئ `GoalApprovalRecord` أو `PlanApprovalRecord`.

## 8. مراجعة أمنية للوظائف الحساسة

هذه الدورة لا تضيف AI، ولا OCR، ولا قراءة ملفات، ولا وسائط، ولا صلاحيات إنتاجية. الخطر الأساسي هو تحويل فحص الجودة إلى قرار آلي أو وزن غير معتمد. لذلك:

- جميع النتائج `review_support_only`.
- لا يوجد score نهائي.
- لا توجد cut scores.
- لا يوجد اعتماد آلي.
- كل بند جودة ينسب إلى معيار داخلي أو مصدر محلي مسجل.

## 11. demo على سيناريو واقعي

سيناريو demo المقبول:

1. متعلم لديه نتائج تقييم رسمي مرفوعة ومراجعة.
2. لديه صوت أسرة وصوت متعلم محفوظان.
3. تظهر مصفوفة مكونات البروفايل في كفاية المعلومات.
4. يفتح المختص إعداد هدف في مجال له تغطية.
5. يحدد باعث الهدف ثم مرتكز الأداء / الخط القاعدي.
6. تظهر Rubric الهدف مع بنود مانعة أو تنبيهات أو تحسينات.
7. عند مراجعة الخطة تظهر Rubric الخطة كوحدة.
8. لا يظهر أي اعتماد إلا عبر مسارات الاعتماد الحالية.

## 12. تحديث سجل القرارات والوثائق

هذه الوثيقة تسجل دورة بناء 05 كدورة تنفيذ لاحقة لا كوثيقة حوكمة حاكمة، لذلك لا تغير ترتيب `himam_governing_files_manifest.json`.

لا تستخدم مسودات GitHub أو Lovable أو محادثات سابقة كأدلة جديدة داخل هذه الدورة إلا إذا سجلت في Evidence Inventory. ما يستخدم حالياً هو ما سبق تسجيله أو ما هو موجود داخل الملفات المحلية للمشروع.
